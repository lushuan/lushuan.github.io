随着 ChatGPT、Claude、Gemini、Cursor、Codex 等 AI 工具越来越普及，很多人开始关注一个问题：

> **怎样写 Prompt，才能让 AI 给出更好的答案？**

网上有大量所谓的“万能提示词”，例如：

> 请先不要回答我的问题。在给出答案时，请先分析我的隐含假设、缺失信息以及常见错误，然后只向我提出一个最关键的问题，等我回答以后再给出最终答案。

这类 Prompt 确实有价值。

但如果只是收集大量 Prompt、复制粘贴所谓的“万能提示词”，其实很容易走偏。

真正值得掌握的并不是某一段固定的 Prompt，而是：

> **如何通过 Prompt 把一个模糊的问题，变成一个明确、可分析、可执行的问题。**

---

## 一、Prompt 真正解决的是什么问题？

很多人认为：

> Prompt 写得越详细，AI 的回答就越好。

这并不完全正确。

Prompt 的核心价值不是“告诉 AI 更多内容”，而是**减少任务中的不确定性**。

例如：

> Redis 和 MySQL 有什么区别？

这是一个比较宽泛的问题。

如果改成：

> 我正在设计一个 Web 应用的数据存储方案，请从数据模型、事务能力、查询方式、性能、持久化、运维复杂度和典型使用场景几个维度比较 Redis 和 MySQL，并说明什么情况下应该选择哪一个。

第二个问题不一定比第一个问题“更高级”，但它明确了：

- 背景
- 任务
- 比较对象
- 比较维度
- 最终目的

因此 AI 更容易给出有针对性的答案。

所以可以把 Prompt 理解成：

> **人与 AI 之间的任务说明书。**

---

## 二、并不是所有问题都需要复杂 Prompt

这是首先需要建立的认识。

可以把问题简单分成三类。

### 1. 简单事实问题

例如：

> Linux 如何查看当前目录？

直接提问即可。

没有必要套一大段 Prompt。

---

### 2. 复杂知识问题

例如：

> Kubernetes 中 Deployment、StatefulSet 和 DaemonSet 有什么区别？

这时候可以增加：

- 使用场景
- 对比维度
- 示例
- 常见误区

这样回答会更加完整。

---

### 3. 复杂决策问题

例如：

> 一个中小型项目应该选择 MySQL 还是 PostgreSQL？

这种问题就不应该只让 AI 罗列区别。

因为真正的问题不是：

> “它们有什么区别？”

而是：

> **“在什么条件下应该选择哪个？”**

这时候就需要让 AI 建立决策模型。

---

## 三、最值得掌握的 8 类 Prompt

与其收藏几十个所谓的“万能 Prompt”，不如掌握几种可以反复组合使用的 Prompt 模式。

---

### 1. 目标澄清 Prompt

### 解决什么问题？

有些时候，用户提出的问题并不一定等于真正想解决的问题。

例如：

> 我要不要学习 Rust？

表面上是在问“学不学 Rust”。

但真正的问题可能是：

> 我未来应该把学习时间投入在哪些技术方向？

这时候可以让 AI 先判断目标。

### Prompt

```text
请先判断我的问题是否已经明确了真正的目标。

请区分：
1. 我表面上提出的问题
2. 我可能真正想解决的问题
3. 我最终需要做出的决策

如果目标存在明显歧义，只向我提出一个最关键的问题。

如果目标已经足够明确，则直接回答，不要为了提问而提问。

我的问题是：

[问题]
```

### 适用场景

- 职业选择
- 技术选型
- 学习规划
- 产品选择
- 项目规划
- 个人决策

---

## 四、挑战假设 Prompt

这是非常值得掌握的一类。

人提出问题时，经常会不自觉地把某些假设当成事实。

例如：

> “这个系统性能很差，所以应该重构。”

这里实际上包含了多个假设：

- 性能确实存在问题；
- 性能问题来自系统架构；
- 重构可以解决问题；
- 重构的成本低于继续维护；
- 没有更简单的解决方案。

如果这些前提中有一个不成立，最终结论就可能错误。

### Prompt

```text
不要默认接受我的判断。

请先分析：

1. 我的判断建立在哪些隐含假设之上？
2. 哪些假设可能是不成立的？
3. 有哪些事实可以证明或推翻这些假设？
4. 这个问题最容易出现什么认知偏差？
5. 有没有比我当前方案更简单的解决方案？

最后再给出你的结论。

我的判断是：

[判断]
```

### 适用场景

特别适合：

- 技术方案
- 架构设计
- 项目决策
- 产品选择
- 工作决策
- 购买决策

---

## 五、方案比较 Prompt

这是工作中非常高频的一类。

很多人会问：

> A 和 B 有什么区别？

但真正需要的往往是：

> **我应该选择 A 还是 B？**

因此不要只要求 AI 罗列优缺点，而应该要求建立决策模型。

### Prompt

```text
请不要简单罗列 A 和 B 的优缺点。

请根据我的实际场景建立一个决策模型。

从以下维度比较：

- 适用场景
- 成本
- 复杂度
- 学习成本
- 运维成本
- 性能
- 可扩展性
- 故障风险
- 团队要求
- 长期维护成本

然后说明：

1. 什么情况下应该选择 A
2. 什么情况下应该选择 B
3. 当前场景更适合哪个
4. 如果未来条件发生什么变化，需要重新做选择

我的场景：

[场景]

候选方案：

A：[方案 A]

B：[方案 B]
```

### 适用场景

例如：

- MySQL vs PostgreSQL
- SQLite vs MySQL
- Docker Compose vs Kubernetes
- GitHub Pages vs Cloudflare Pages
- 单体架构 vs 微服务
- 自建服务 vs 云服务

---

## 六、代码审查 Prompt

代码审查是 AI 非常适合辅助的场景。

但如果只问：

> “帮我看看这段代码有什么问题？”

AI 往往会关注一些比较表面的内容。

可以明确审查维度。

### Prompt

```text
请以资深软件工程师和代码评审者的角度审查下面的代码。

不要只检查语法和明显 Bug，请分别从以下维度分析：

1. 正确性
2. 并发安全
3. 错误处理
4. 资源管理
5. 性能
6. 可读性
7. 可测试性
8. 接口设计
9. 模块职责
10. 可维护性

对于发现的问题，请标记：

[P0] 必须立即修复
[P1] 建议尽快修复
[P2] 可以后续优化

每个问题说明：

- 问题是什么
- 为什么是问题
- 可能造成什么后果
- 推荐修改方式

不要为了代码风格而强行提出重构建议。

代码：

[代码]
```

这里最后一句非常重要。

AI 很容易把：

> “可以优化”

误认为：

> “应该马上重构”。

但在真实项目中，**可优化不等于值得修改**。

---

## 七、陌生项目分析 Prompt

当面对一个陌生代码库时，不应该一上来就让 AI 修改代码。

第一步应该是：

> **建立项目地图。**

可以使用这样的 Prompt：

```text
我正在分析一个陌生的软件项目。

不要立即修改代码。

请按照以下顺序进行分析。

第一阶段：项目侦察

- 技术栈
- 项目入口
- 启动流程
- 核心模块
- 数据库
- 配置
- 外部依赖

第二阶段：建立系统地图

- 模块之间的依赖关系
- 核心业务流程
- 核心数据模型
- 关键接口
- 主要调用链路

第三阶段：识别风险

- 高风险代码
- 高耦合模块
- 隐式业务规则
- 缺失测试
- 文档缺失
- 可能影响生产环境的问题

第四阶段：

按照优先级给出后续调查建议。

要求：

不要为了完整而分析所有代码。
优先识别理解整个项目最关键的部分。
```

这个思路实际上非常适合 AI Agent。

可以概括成：

> **先理解，再规划，最后修改。**

而不是：

> **打开代码 → 直接修改。**

---

## 八、学习知识 Prompt

AI 不仅可以回答问题，也可以充当“老师”。

但：

> “给我介绍一下 Go Channel。”

通常只能得到一篇知识介绍。

如果希望真正理解一个概念，可以这样问：

```text
请把我当成一个已经具备一定编程经验，但对这个概念理解还不深入的学习者。

请按照以下方式教学：

1. 先用直觉解释
2. 再解释底层原理
3. 给出最小代码示例
4. 给出真实工程场景
5. 解释什么时候应该使用
6. 解释什么时候不应该使用
7. 说明常见误区
8. 最后给出 3 个问题测试我是否真正理解

不要一开始堆砌大量专业术语。

我要学习的概念是：

[概念]
```

这种方式特别适合学习：

- 编程语言
- 数据库
- Linux
- 网络
- Docker
- Kubernetes
- 分布式系统
- AI
- 计算机基础

---

## 九、反例学习 Prompt

这是非常值得推荐的一种学习方式。

因为：

> **知道正确答案，并不代表真正理解。**

例如学习一个 API，只看正确用法，很容易产生“我已经懂了”的错觉。

可以要求 AI 同时给出反例。

### Prompt

```text
请通过正例和反例帮助我理解下面这个概念。

请分别给出：

1. 一个正确的例子
2. 一个看起来正确但实际上错误的例子
3. 一个容易被误用的例子
4. 一个生产环境中可能踩坑的例子

然后解释这几个例子为什么不同。

概念：

[概念]
```

这种 Prompt 对理解边界尤其有效。

因为很多知识真正难的地方不是：

> **什么时候可以使用。**

而是：

> **什么时候不能使用。**

---

## 十、知识整理 Prompt

AI 很适合把杂乱的信息重新组织成知识体系。

但不要只问：

> “帮我总结一下。”

可以明确要求 AI 建立结构。

### Prompt

```text
请不要简单总结下面的内容。

请把它整理成一个可以长期复用的知识体系。

要求：

1. 提炼核心概念
2. 建立概念之间的关系
3. 区分“必须理解”和“了解即可”
4. 提炼容易混淆的概念
5. 提炼常见误区
6. 提炼实际使用场景
7. 最后给出一个适合作为知识库目录的结构

原始内容：

[内容]
```

它适合处理：

- 文章
- 书籍
- 技术文档
- 会议记录
- 学习资料
- 调研结果
- 网页内容

---

## 十一、信息提取 Prompt

有时候并不是需要 AI “总结”，而是需要从大量文字中找出结构化信息。

例如会议记录、需求文档、聊天记录。

可以使用：

```text
请把下面的信息整理成“可执行信息”，而不是简单总结。

分别提取：

1. 已经确定的事实
2. 已经做出的决定
3. 尚未确定的问题
4. 待办事项
5. 责任人
6. 截止时间
7. 存在的风险
8. 需要进一步确认的信息

特别注意：

不要把讨论中的观点误认为最终决定。
不要把推测写成事实。
如果信息中没有明确说明，请标记为“未知”。

原始内容：

[内容]
```

这种 Prompt 的核心价值是：

> **把非结构化信息转换成结构化信息。**

---

## 十二、一个非常容易被忽视的 Prompt：控制 AI 不要过度回答

AI 有一个天然特点：

> **很容易说得太多。**

有时候用户真正需要的是一个明确结论，但 AI 会扩展出十几个相关知识点。

这时候可以主动限制：

```text
请只回答我的核心问题。

不要主动扩展到无关知识。
不要为了“完整”而罗列大量内容。

如果存在多个方向：
先告诉我最重要的一个。

只有当补充信息会明显影响最终结论时，才展开说明。

如果我的问题存在关键歧义，请先指出歧义。
```

这个 Prompt 看似简单，实际上非常实用。

---

## 十三、把这些 Prompt 组合起来

真正使用的时候，不需要把所有 Prompt 全部复制进去。

例如一个技术选型问题：

```text
背景：
我需要为一个新项目选择数据库。

目标：
选择一个适合当前项目并且长期维护成本合理的方案。

请先检查：
1. 我有哪些隐含假设？
2. 当前信息是否足够？
3. 哪些缺失信息会影响结论？

然后：

1. 比较候选方案
2. 建立决策模型
3. 给出推荐
4. 说明推荐成立的前提
5. 给出未来什么情况下应该重新评估

不要为了完整而罗列与决策无关的内容。

候选方案：
A：[方案 A]
B：[方案 B]
C：[方案 C]
```

这比寻找一个“数据库选型万能 Prompt”更加灵活。

---

## 十四、一个通用 Prompt 框架

如果不想记住上面的具体 Prompt，可以记住下面这个结构：

```text
角色：
请以 [角色] 的角度分析。

背景：
[当前情况]

目标：
我希望解决 [问题]。

约束：
[预算 / 技术栈 / 时间 / 团队 / 其他限制]

任务：
请完成 [具体任务]。

分析维度：
请从 [维度 1 / 维度 2 / 维度 3] 分析。

输出：
请按照 [表格 / 分点 / 步骤 / 方案] 输出。

判断标准：
请优先考虑 [成本 / 稳定性 / 性能 / 可维护性 / 风险等]。

其他要求：
[其他约束]
```

可以把它记成：

> **角色 + 背景 + 目标 + 约束 + 任务 + 维度 + 输出 + 判断标准**

不需要每次全部填写。

根据问题复杂程度选择其中几个即可。

---

## 十五、比“万能 Prompt”更重要的，是判断什么时候使用什么 Prompt

可以建立一个非常简单的对应关系：

| 遇到的问题 | 优先使用 |
|---|---|
| 我到底想解决什么？ | 目标澄清 |
| 我是不是想错了？ | 假设审查 |
| A 和 B 怎么选？ | 方案决策 |
| 代码有什么问题？ | Code Review |
| 陌生项目怎么看？ | 项目侦察 |
| 怎么真正理解一个概念？ | 深度学习 |
| 我真的理解了吗？ | 反例学习 |
| 信息太乱怎么办？ | 知识整理 |
| 会议内容太乱怎么办？ | 信息提取 |
| AI 说得太多怎么办？ | 输出约束 |

这样比收藏几百条 Prompt 更有价值。

## 十六、给出的那个 Prompt，为什么值得借鉴？

回到文章开头那个 Prompt。

它真正有价值的地方，其实不是：

> “请先不要回答。”

而是它包含了一个非常好的思维过程：

```text
问题
 ↓
检查隐含假设
 ↓
发现缺失信息
 ↓
识别常见错误
 ↓
确认真实目标
 ↓
最终回答
```

这实际上是一种**问题诊断流程**。

不过原来的 Prompt 有一个可以优化的地方：

> **不应该要求 AI 无论如何都必须先问一个问题。**

因为有些问题已经足够明确。

因此更好的版本应该是：

```text
请先判断我的问题是否已经具备足够的信息。

如果信息已经足够：
直接回答，不要为了遵循提示词而额外提问。

如果信息不足：
1. 指出关键隐含假设；
2. 指出缺失信息，并说明它可能如何影响结论；
3. 指出此类问题最容易出现的错误；
4. 只提出一个最关键的问题。

如果缺失的信息无法通过一个问题解决：
请基于当前信息给出初步判断，并明确说明你的假设。

回答时：
- 不要默认接受我的前提；
- 区分事实、推测和建议；
- 不要为了完整而扩展无关内容；
- 如果存在多个方案，请说明选择条件，而不是简单给出“最佳方案”。

我的问题是：

[问题]
```

这个版本更适合长期使用。

## 十七、Prompt 的终点，其实不是“Prompt 工程”

如果把 AI 使用能力简单分成几个阶段，大致可以这样理解：

```text
第一阶段
“告诉我答案”
        ↓
第二阶段
“按照这些要求告诉我答案”
        ↓
第三阶段
“先帮我分析问题，再告诉我答案”
        ↓
第四阶段
“帮我建立判断模型，然后和我一起做决定”
```

真正高价值的场景，通常发生在第三、第四阶段。

因此，与其背诵大量 Prompt，不如在提问之前先思考五个问题：

### ① 我真正想解决什么？

### ② 我现在默认了哪些前提？

### ③ 哪些关键信息还不知道？

### ④ 我是想获得知识，还是要做一个决策？

### ⑤ 我希望 AI 最终产出什么？

这五个问题本身，就是一种非常重要的 Prompt 能力。

---

## 十八、最后：Prompt 是“认知脚手架”，不是咒语

很多 Prompt 看起来非常神奇：

> “你现在是一名世界顶级专家……”

> “请进行深度思考……”

> “请从第一性原理分析……”

这些表达有时候有帮助，但不要把它们理解成某种“咒语”。

真正决定答案质量的，通常还是：

- 问题是否明确
- 背景是否充分
- 目标是否明确
- 约束是否清楚
- 判断标准是否明确
- 输出形式是否合适
- 是否允许 AI 质疑错误前提

所以，**Prompt Engineering 最值得学习的并不是“背 Prompt”，而是“设计问题”。**

一个好的 Prompt，本质上是在完成这样一件事情：

> **把人的模糊意图转换成 AI 可以执行的任务。**

而更进一步：

> **一个好的 AI 使用者，不一定是拥有最多 Prompt 的人，而是最知道什么时候应该让 AI 回答、什么时候应该让 AI 反问、什么时候应该让 AI 质疑自己、什么时候应该让 AI 帮助自己建立决策模型的人。**

这可能才是生成式 AI 时代真正值得培养的能力。
