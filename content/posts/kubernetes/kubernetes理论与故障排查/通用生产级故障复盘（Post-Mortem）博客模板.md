# 📚 通用生产级故障复盘（Post-Mortem）博客模板

## # 标题：[故障级别/标签] 记一次 [组件/系统名] 引起的 [核心现象] 原地抢救实录

> 用 2-3 句话简要交代这场事故发生的背景、最惊险的惨状，以及你坚持的最高原则（例如：不扩大的无损修复）。字数不宜多，目的是快速抓住读者的好奇心。

## ## 2. 顺藤摸瓜：多维度排查与见招拆招 (The Exploration)

> **💡 提示：**
> 如果排查过程经历了多个波折，建议像剥洋葱一样，采用“分阶段/分层”的递进逻辑来写。

### 2.1 阶段一：打破第一道迷雾 —— 下沉到 [底层/运行时]

* **排查思路**：当常规的高层工具（如 `kubectl` / 应用 API）失效时，如何寻找新的突破口？
* **诊断命令与工具**：
```bash

```


* **核心破局点 1**：你通过查看哪些隐蔽的日志、残留文件或内核参数，推翻了表象，抓到了第一个真实根因？

### 2.2 阶段二：遭遇 [复合死锁/次生故障] 拦截

* **次生现象**：第一层问题刚解决或刚有眉目，系统又抛出了什么更诡异的新限制（例如：系统保护污点、路由不可达、配置冲突）？
* **深入诊断（分析临终遗言）**：
```bash

```


* **死锁逻辑链剖析**：清晰地画出或用文字理出系统陷入的**循环死锁逻辑**（例如：因为 A 挂了导致 B 不通，因为 B 不通导致 A 无法启动）。

## ## 4. 架构反思：探寻组件背后的深度演进设计 (Deep Dive)

> **💡 提示：**
> 这一章是把你博客的含金量拉满的关键。不要停留在“问题解决了”，要拔高到**组件或系统的设计理念**上。

* **提出深度问题**：为什么官方/开源社区要把这个组件设计得这么复杂（例如：为什么要拆分成 3 个 Namespace、为什么要强制引入 Operator）？
* **架构层面的收益剖析**：从以下几个维度，客观论述这种设计的合理性与长远优势：
* **管理面与数据面的解耦**
* **最小特权原则与安全隔离**
* **故障自愈（Self-healing）与平滑升级能力**

## ## 5. 经验沉淀：故障生存指南与避坑金律 (Post-Mortem Summary)

### 📋 黄金排查工具箱 (TL;DR)

提炼出在本次故障的极端盲区中，哪几个命令和参数是真正救命的，做成一张速查表：

| 故障场景/盲区 | 绝杀工具/命令 | 核心价值 |
| --- | --- | --- |
| **应用/API 瘫痪时** | `your-low-level-command` | 绕过上层封装，直面最底层运行时 |
| **应用启动即崩时** | `your-previous-logs-command` | 捕捉容器/进程临死前的最后一句话 |
| **陷入网络死锁时** | `hostNetwork / bypass-config` | 降维打击，用基础网络奶活虚拟网络 |

### 🧠 DevOps 避坑金律

1. **[金律一]**：不要盲目依赖自动化组件的默认策略，极端场景下，显式指定 [物理/确定性参数] 才是唯一出路。
2. **[金律二]**：保持对系统和运行时底层的敬畏，当高层逻辑失明时，条件反射般下沉到内核和运行时去抓线索。
3. **[金律三]**：**严禁盲目执行破坏性重置**。精细的外科手术式修复，才是检验一个 DevOps/SRE 工程师含金量的试金石。

## 💾 为什么这套模板具备高复用性？

1. **结构“黄金三段论”**：任何技术事故，本质上都是 **“出事了 ➔ 怎么查的 ➔ 以后怎么防”**。这套模板严格契合了这个心智模型。
2. **重点突出“转折点”**：在第 2 章节中特别留出了“次生故障/复合死锁”的位置，因为在真实的生产排查中，很少有一竿子插到底的顺利，往往是解开一个谜题又遇到一个新坑，这个结构能完美还原排查思路的严密性。
3. **技术博文的“高级感”**：第 4 章节的“架构反思”可以将一篇普通的“填坑日记”直接升华为一篇“深度技术架构分析文”，非常有利于沉淀为你博客的招牌技术资产。
